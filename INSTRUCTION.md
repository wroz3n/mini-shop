# Инструкция: мини-магазин на Flask с модулем тестирования и CI/CD

## 1. Что это за проект

Учебный мини-интернет-магазин: каталог товаров, регистрация и вход,
оформление заказа, промокод. Главная ценность проекта — модуль
тестирования и CI/CD-пайплайн: при каждом push в ветку `main` на GitHub
автоматически запускаются линтер, тесты с проверкой покрытия и сборка.

Результат: репозиторий на GitHub, в котором вкладка Actions показывает
зелёный прогон, а README содержит бейдж статуса CI.

Стек:

- Python 3.12
- Flask 3.x
- SQLite (встроенный модуль `sqlite3`, файл `app.db`)
- pytest + pytest-cov — тесты и покрытие
- ruff — линтер
- GitHub Actions — CI/CD

## 2. Что понадобится

- Python 3.12 (проверить: `python --version` или `python3 --version`).
- Git (проверить: `git --version`).
- Аккаунт на GitHub.
- Доступ в интернет для установки зависимостей и для GitHub Actions.

## 4. Установка и запуск локально

Выполнять из папки проекта `mini-shop`.

### 4.1. Создать виртуальное окружение и установить зависимости

```bash
python -m venv .venv
```

Активация:

```bash
# Windows
.venv\Scripts\activate

# macOS / Linux
source .venv/bin/activate
```

Установка зависимостей:

```bash
pip install -r requirements.txt
pip install -r requirements-dev.txt
```

### 4.2. Запустить приложение

```bash
flask --app "app.main:create_app" run
```

Открыть в браузере http://127.0.0.1:5000

Должно быть видно:

- заголовок «Мини-магазин»;
- список товаров с ценой и остатком (загружается с `GET /api/products`);
- поле промокода и кнопка «Оформить заказ»;
- форма регистрации / входа.

При первом запуске база `app.db` создаётся автоматически и заполняется
6 демо-товарами: «Ноутбук» (59999 ₽), «Мышь» (1499 ₽), «Клавиатура»
(3499 ₽), «Монитор» (18999 ₽), «Наушники» (4999 ₽), «Веб-камера» (2999 ₽).

Остановить сервер: `Ctrl+C` в терминале.

### 4.3. Проверить API вручную (curl)

В отдельном терминале, пока сервер запущен:

```bash
# Список товаров
curl http://127.0.0.1:5000/api/products

# Регистрация
curl -X POST http://127.0.0.1:5000/api/register \
  -H "Content-Type: application/json" \
  -d '{"username": "demo_user", "password": "demo123"}'
# Ожидается: {"message": "ok"} и статус 201

# Вход
curl -X POST http://127.0.0.1:5000/api/login \
  -H "Content-Type: application/json" \
  -d '{"username": "demo_user", "password": "demo123"}'
# Ожидается: {"message": "ok"} и статус 200

# Заказ: 1 ноутбук со скидкой SALE10
curl -X POST http://127.0.0.1:5000/api/orders \
  -H "Content-Type: application/json" \
  -d '{"user_id": 1, "items": [{"product_id": 1, "quantity": 1}], "promo": "SALE10"}'
# Ожидается: {"message": "ok", "order_id": 1, "total": 53999.1} и статус 201

# Ошибка: несуществующий товар
curl -X POST http://127.0.0.1:5000/api/orders \
  -H "Content-Type: application/json" \
  -d '{"user_id": 1, "items": [{"product_id": 999, "quantity": 1}]}'
# Ожидается: {"error": "Товар 999 не найден"} и статус 400
```

Все ошибки API возвращают JSON вида `{"error": "..."}` на русском,
без traceback.

## 5. API — справочник

| Метод и путь | Тело запроса | Успех | Ошибки |
|---|---|---|---|
| `GET /` | — | 200, HTML-страница | — |
| `GET /api/products` | — | 200, список `id`, `name`, `price`, `stock` | — |
| `POST /api/register` | `{"username", "password"}` | 201, `{"message": "ok"}` | 400 — неверный логин/пароль или логин занят |
| `POST /api/login` | `{"username", "password"}` | 200, `{"message": "ok"}` | 401 — неверный логин или пароль |
| `POST /api/orders` | `{"user_id", "items": [{"product_id", "quantity"}], "promo"}` | 201, `{"message": "ok", "order_id", "total"}` | 400 — нет товара, не хватает остатка, пустой заказ |

Правила валидации:

- Логин: 3–20 символов, только латинские буквы, цифры и `_`.
- Пароль: не менее 6 символов и хотя бы одна цифра.
- Пароль хранится только в виде хеша (`werkzeug.security`).
- Промокод `SALE10` даёт скидку 10%. Любой другой промокод или пустое
  значение — без скидки.
- При оформлении заказа остаток товара уменьшается, сумма считается
  через `calculate_total` и округляется до 2 знаков.

## 6. Бизнес-логика (`app/services.py`)

Чистые функции без Flask — их удобно тестировать:

- `calculate_total(items)` — сумма `price * quantity` по позициям,
  округление до 2 знаков. Пустой список — `0.0`. Отрицательная цена
  или количество <= 0 — `ValueError`.
- `check_stock(product_stock, quantity)` — `True`, если остатка хватает.
  Количество <= 0 — `ValueError`.
- `apply_discount(total, promo)` — `SALE10` даёт скидку 10%, остальное —
  без скидки. Итог не может быть отрицательным.
- `validate_username(username)` — `True` только для 3–20 символов:
  латиница, цифры, `_`.
- `validate_password(password)` — `True` только при длине от 6 символов
  и хотя бы одной цифре.

## 7. База данных (`app/database.py`)

SQLite, файл `app.db` в корне проекта, создаётся при старте приложения.

- `users`: `id`, `username` (уникальный), `password_hash`, `created_at`.
- `products`: `id`, `name`, `price` (>= 0), `stock` (>= 0).
- `orders`: `id`, `user_id` (внешний ключ на `users`), `total` (>= 0),
  `created_at`.
- `order_items`: `id`, `order_id`, `product_id`, `quantity` (> 0),
  `price` (>= 0).

Внешние ключи включены (`PRAGMA foreign_keys = ON`), ограничения
`CHECK` отклоняют отрицательные цены и остатки.

## 8. Тесты

### 8.1. Запуск

```bash
pytest -v
```

Ожидаемый результат: **52 passed**, время прогона — около 2 секунд.

### 8.2. Покрытие

```bash
pytest --cov=app --cov-report=term-missing
```

Ожидаемый результат: покрытие **около 93%**. Порог в пайплайне — не
менее 80% (`--cov-fail-under=80`), при покрытии ниже порога тесты
считаются непройденными.

### 8.3. Линтер

```bash
ruff check app tests
```

Ожидаемый результат: `All checks passed!`

### 8.4. Как устроены тесты

- `tests/test_services.py` (30 тестов) — юнит-тесты: обычные наборы,
  пустой список, округление, отрицательные значения, граничные длины
  логина и пароля, кириллица и пробел в логине.
- `tests/test_api.py` (15 тестов) — интеграционные тесты через Flask
  `test_client`: товары, регистрация (успех, дубль, короткий пароль),
  вход (успех, неверный пароль, неизвестный пользователь), заказы
  (успех и уменьшение остатка, промокод, несуществующий товар,
  превышение остатка, неизвестный пользователь, пустой заказ).
- `tests/test_database.py` (7 тестов) — создание таблиц и демо-товары,
  уникальность `username`, отклонение отрицательной цены и остатка,
  отклонение заказа с несуществующим `user_id`, количество в позиции
  заказа больше нуля.
- `tests/conftest.py` — фикстуры: временная БД в `tmp_path`, тестовое
  приложение `create_app` с тестовой конфигурацией, тестовый клиент.
  Тесты не зависят от реального файла `app.db` и не зависят от порядка
  запуска.

### 8.5. Проверка «красного» прогона (доказательство, что тесты работают)

1. В `tests/test_services.py` временно изменить одно ожидаемое значение,
   например в тесте скидки `900.0` на `901.0`.
2. Запустить `pytest -q` — должен быть 1 failed.
3. Вернуть значение обратно.
4. Запустить `pytest -q` — снова все тесты зелёные.

Если сломанный тест не даёт красного прогона — тесты не подключены
к проверяемому коду, и это нужно исправить, а не скрывать.

## 9. CI/CD-пайплайн (GitHub Actions)

Файл `.github/workflows/ci.yml`. Триггер: `push` и `pull_request`
в ветку `main`.

### 9.1. Job `test`

1. `actions/checkout@v4` — получить код.
2. `actions/setup-python@v5` — Python 3.12, кэш pip (`cache: 'pip'`).
3. `pip install -r requirements.txt -r requirements-dev.txt`.
4. `ruff check app tests`.
5. `pytest --cov=app --cov-report=term-missing --cov-fail-under=80`.
6. `python -c "from app.main import create_app; create_app()"` —
   проверка, что приложение стартует.

### 9.2. Job `build`

- Зависит от `test` (`needs: test`).
- Архивирует исходники без `app.db`, `__pycache__` и `.venv` и загружает
  артефакт `mini-shop` через `actions/upload-artifact@v4`.

Важная деталь: архив создаётся в `/tmp/mini-shop.tar.gz`, а не внутри
папки проекта. Если писать архив внутрь архивируемой папки, `tar`
падает с ошибкой `file changed as we read it`, и job `build` становится
красным.

### 9.3. Где смотреть результат

В репозитории на GitHub: вкладка **Actions** → прогон **CI**.
Зелёный прогон: оба job (`test` и `build`) — зелёные.
Статус также показывает бейдж в начале `README.md`:

```markdown
![CI](https://github.com/<username>/mini-shop/actions/workflows/ci.yml/badge.svg)
```

Перед `<>` в ссылке нужно подставить свой GitHub-ник вместо
`<username>`.

## 10. Публикация на GitHub

### 10.1. Создать репозиторий

1. На GitHub: **New repository**, имя `mini-shop`, **Public**.
2. Не ставить галочки README, .gitignore и лицензию — репозиторий
   должен быть пустым, файлы загрузятся из проекта.

### 10.2. Отправить код

Из папки проекта:

```bash
git init
git branch -M main
git add .
git commit -m "Интеграция модуля тестирования и CI/CD-пайплайна: мини-магазин на Flask"
git remote add origin https://github.com/<username>/mini-shop.git
git push -u origin main
```

Вместо `<username>` — свой GitHub-ник. Он же должен стоять в бейдже CI
в `README.md` и в ссылке выше.

### 10.3. Проверить прогон

1. Открыть вкладку **Actions** в репозитории.
2. Дождаться завершения прогона **CI** (обычно меньше минуты).
3. Убедиться, что `test` и `build` зелёные и что во вкладке прогона
   есть артефакт `mini-shop`.

### 10.4. Если прогон красный

1. Открыть упавший job, прочитать лог шага, на котором он упал.
2. Исправить причину локально.
3. Проверить локально: `ruff check app tests` и
   `pytest --cov=app --cov-fail-under=80`.
4. Сделать новый коммит и `git push` — прогон запустится заново.

## 11. Частые проблемы и решения

| Проблема | Причина и решение |
|---|---|
| `pytest` не найден | Не активировано виртуальное окружение или не установлены dev-зависимости: активировать `.venv` и выполнить `pip install -r requirements-dev.txt`. |
| `ModuleNotFoundError: No module named 'flask'` | Не установлен Flask: `pip install -r requirements.txt` в активированном `.venv`. |
| Порт 5000 занят | Другой сервер уже запущен на этом порту. Остановить его или запустить Flask на другом порту: `flask --app "app.main:create_app" run --port 5001`. |
| `app.db` попал в коммит | Файл должен быть в `.gitignore`. Удалить его из индекса: `git rm --cached app.db`, затем сделать коммит. Сам файл `app.db` при этом останется на диске и будет пересоздан при запуске. |
| Тесты используют реальную БД | Такого быть не должно: `conftest.py` подменяет путь к БД на временный файл в `tmp_path`. Проверить, что тесты запускаются из корня проекта. |
| CI красный на шаге `tar` | Архив нельзя создавать внутри архивируемой папки. В `ci.yml` архив должен писаться в `/tmp/mini-shop.tar.gz`, а в `upload-artifact` должен быть указан путь `/tmp/mini-shop.tar.gz`. |
| GitHub не принимает изменение `ci.yml` через API | Это ограничение GitHub: workflow-файлы нельзя менять через API без отдельного разрешения workflow. Править `ci.yml` нужно через веб-интерфейс GitHub (открыть файл → Edit) или обычным `git push` из локального репозитория. |
| GitHub просит двухфакторную проверку при входе | Подтвердить вход в приложении GitHub Mobile, выбрав показанное на экране число. |
